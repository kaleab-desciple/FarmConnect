1 — Executive summary
Farm-to-product maturity assessment
Summary

Current platform covers many functional areas (farm/field management, crop lifecycle, AI diagnostics, weather) and is well-structured by Clean Architecture. However, the farm-to-product flow lacks production-grade traceability, QA, and post‑harvest operational maturity required to run a multi‑tenant farmer–merchant marketplace at scale.
Key gaps: insufficient harvest → batch → product lineage, minimal smallholder aggregation logic, weak auditability and tamper-resistance for field-level events, incomplete financial linkage at farm/field granularity, and limited offline-first/edge data reconciliation patterns.
Impact: without these operational efficiency (weighing, aggregation, settlement) will be poor; scaling to thousands of smallholders or integrating finance/logistics will be risky.
Scorecard (high-level)

Traceability (farm→product): Weak — lineage exists conceptually but not enforced as immutable lineage with batch IDs and QC anchors.
grading: Minimal — grading workflows and lab/cert linkage missing.
xxxxxxxxx Aggregation/scale for smallholders: Weak — no formal aggregator entity, reconciliation, or split-payment primitives.
Offline & field operations: Partial — activity logs exist but offline sync/reconciliation and trusted evidence (geo/EXIF, signatures) are not robust.
xxxxxxx Financial linkage: Partial — escrow exists but farm-level cost/ledger integrations and per-batch settlement not modeled.
xxxxxxx Audit & tamper resistance: Weak — no append-only event store or signed audit chain for critical steps.

Consequence

xxxxxx Merchant risk, disputes, and post-sale returns/loss risk increase.
xxxxxx Slow merchant adoption and poor price discovery.
xxxxxx Settlement friction and regulatory/compliance exposure.
Recommended high-level priorities (first 90 days)

Implement HarvestBatch entity + immutable lineage & product mapping (High).
Add QC/Grading workflow and lab/cert linkage into product approval (High).
Build Aggregator concept + smallholder reconciliation & split settlement (High).
Improve offline sync model and evidence capture (geo/EXIF/weights) (Medium).
Introduce event-driven change log / append-only audit for critical events (Medium).
Add farm-level financial accounts & per-batch settlement metadata (Medium).

5 — Real-world benchmark alignment
Where the system stands vs production-grade agri-marketplaces

Traceability: Production systems (Twiga, AgroStar, larger agri-traceability systems) enforce batch-level provenance, lab integration, and immutable audit trails. Recommendation: match by adding HarvestBatch + BatchQC + signed lab reports.
QA/Credentialing: Marketplaces require certificates or lab tests for many commodities. Recommendation: integrate lab APIs and certificate issuers, and render certificate badges in product listings.
Smallholder aggregation: Mature platforms treat aggregators as first-class objects with reconciliation and split payments. Recommendation: add Aggregator and per-member contribution records and automated split settlement.
Offline & field UX: Successful platforms invest in resilient mobile sync and evidence capture; local queues + resumable media uploads are essential.
Financial & settlement integration: Production-grade platforms integrate escrows, payouts, and microfinance modules referenceable to batches/listings.
Compliance & audit: Products sold with claims (organic, low-aflatoxin) are supported with signed certificates and chain-of-custody.
Concrete production references (patterns to copy)

Use PostGIS + versioned polygons for fields (cadastral-grade).
Enforce batch sealing with multi-proof checks (photo+geo+weighbridge receipts).
Use QC sample chain-of-custody: sample_id -> lab_input -> lab_report -> certificate -> link to batch.

7 — Operational and technical considerations (risks & mitigations)
Scalability & performance

Risk: spatial queries and heavy media volumes slow down UI and aggregation.
Mitigation: PostGIS indexes, tile-based polygon storage for large geometries, CDNs and signed URLs for media, background processing for heavy QC tasks.
Risk: event store growth and read model lag.
Mitigation: retention/archival policies, snapshotting, partitioned topics.
Data consistency & concurrency

Use per-entity version numbers and optimistic locking for critical resources (batch sealing, listing state).
Use eventual consistency for KPIs; strict consistency for financial settlement.
Security & anti-fraud

Enforce signed attachments metadata, limit manual overrides to Manager/Admin with audit trail, random QC spot checks.
Use two-factor confirmations for high-value seal/settle operations.
Offline-first constraints

Use monotonic client-generated ids, idempotency keys, and server reconciliation with conflict resolution UI. Critical actions (settle funds) should be prohibited offline — require connectivity.
Auditability & legal compliance

Append-only audit events with chained hashes; keep raw evidence for statutory retention periods.

Key Implementation Details
1. Database Tables & Schema (harvest_events_v1.py)
harvest_events - Field-level harvests with weight, moisture, photos, location

2. Business Rules & Flow
HarvestEvent: Written when farmer records harvest (evidence: photos OR weighbridge receipt required)
HarvestBatch: Created DRAFT, contributions added while DRAFT
Seal Operation (harvest_batch_repo.py):
Uses SELECT FOR UPDATE to serialize concurrent seals
Validates no harvest events already in sealed batches
Computes deterministic lineage_hash (SHA256 of sorted contributions)
Calculates weighted average moisture
Sets status=SEALED, records sealed_at, sealed_by, seal_evidence
3. Immutability Enforcement
DB Trigger (harvest_events_v1.py): Blocks INSERT/UPDATE/DELETE on contributions when batch is SEALED
Application-level (harvest_batch_repo.py): Validates batch status before adding contributions
4. Product Listing Guards (guards.py)
Prevents product creation unless harvest batch is QC_PASSED
Validates all linked batches before publishing listings
5. End-to-End Flow
Farmer records harvest → harvest_events INSERT
Aggregator creates batch (DRAFT) → harvest_batches INSERT
Aggregator adds contributions → harvest_batch_contributions INSERT (while DRAFT)
Aggregator seals batch → harvest_batches UPDATE (SEALED + lineage_hash)
Lab submits QC → batch_qc_reports INSERT + harvest_batches status update
Product created from sealed QC_PASSED batch → product listing allowed

Reworked the harvest -> product conversion to use the new harvest-batch, immutable-lineage and QC flows.
Key behaviors:
When converting a legacy Harvest to a product the service now:
Creates a HarvestEvent from the legacy harvest record.
Creates a draft HarvestBatch and adds the event as a contribution.
Seals the batch (computes lineage hash, aggregated weight, moisture average).
Sets the batch to QC_PENDING.
If inline QC data is provided in product_data["qc_report"], it creates a QC report for the batch (which may change batch status to QC_PASSED or QC_FAILED).
If the harvest batch has passed QC:
Creates the product via the existing ProductService.create_product (which validates harvest-batch rules).
Creates a ProductBatch for inventory and links it to the harvest batch using HarvestBatchRepository.link_product_batch_to_harvest_batch.
If the batch has not yet passed QC:
Creates the Product record but keeps it inactive (is_active=False) and includes lineage metadata (harvest_batch_id) so it can be activated once QC completes.

If product_data contains:
harvest_batch_id — the code will use that batch instead of creating a new one.
qc_report — the code will attempt to create an inline QC report (non-fatal if it fails).
batch_code, batch_notes, batch_metadata, product_batch_code, seal_evidence — these are used to populate the batch/product batch.
When the batch is not QC_PASSED, the product is created inactive (is_active=False). This avoids creating sellable listings without QC. When QC is later created and passes, you can activate the product (or re-run ProductService.create_product if you prefer).
I intentionally kept QC creation non-fatal so the conversion won’t fail if the lab data is missing or malformed; this mirrors typical real-world workflows where QC is a separate step.
How to test locally (quick smoke)

The repo includes a smoke script for batch flows: harvest_batch_flow.py. You can run it inside your API container or local environment (make sure env variables and DB are configured).
To exercise the new path with a legacy Harvest record:
Call the harvest conversion route (your existing route is POST /harvests/{harvest_id}/convert-to-product) with a payload similar to: { "name": "My crop product", "quantity": 100, "base_price": 1.5, "currency": "USD", "batch_code": "BATCH-1234", // optional qc report to auto-create QC: "qc_report": { "lab_id": "LAB-001", "metrics": {"moisture": 12.3}, "passed": true } }
If QC is passed the response will be the created product DTO (active). If QC is pending the returned product will be created but inactive (and its metadata will include harvest_batch_id).
For programmatic tests, you can reuse the pattern in harvest_batch_flow.py which demonstrates event->batch->seal->qc->product_batch linking.
